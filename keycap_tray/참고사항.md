## 1. 동작 중에 알람(빨간불)이 나는 경우

**현재 처리 (2026-11-02 반영)**
- 움직이기 전, 명령이 무시됐을 때, 목표에 못 갔을 때, 단계가 끝났을 때 **알람을 자동으로 해제**해요.
- 화면에 어떤 알람이었는지 찍혀요. 알람 번호와 이름은 Dobot 공식 알람 설명서 기준이에요.

| 번호 | 뜻 | 해제만으로 되나 | 우리가 할 일 |
|---|---|---|---|
| 0x00~0x01 | 재시작 후 남은 알람 / 알 수 없는 명령 | 됨 | 자동 해제 |
| 0x02~0x04 | 파일 시스템 / 내부 통신 / 각도 센서 오류 | 안 됨 | 전원 껐다 켜기 |
| 0x10~0x15 | **계획 단계**: 목표점이 특이 자세, 작업 범위 밖, 관절 한계 밖 (0x12가 가장 흔함) | 됨 (팔은 안 움직이고 명령만 거부) | 자동 해제. 같은 자리에서 반복되면 좌표 수정 |
| 0x20~0x22 | **이동 중**: 특이 자세, 작업 범위 벗어남, 관절 한계 넘음 | 됨 | 자동 해제. 반복되면 경로나 좌표 수정 |
| 0x30~0x33 | 관절 속도 초과 (직선 이동 MOVL에서 주로 발생) | 됨 | 자동 해제. 반복되면 속도 낮추기 |
| 0x40~0x49 | 관절이 한계 각도에 닿음 | 반대로 빠져나오면 저절로 풀림 | 손으로 가운데 쪽으로 옮기기 |
| **0x50~0x53** | **탈조(충돌)**: 부딪혀서 모터가 위치를 놓침 | **안 됨. 해제해도 위치가 틀어진 채로 남음** | **홈 복귀 필수** (`demo.py home`) |

- 2026-11-02 실측
  - 0x12: 세트1이 133.7°(관절1 한계 근처)로 갈 때, 세트2가 반경 199mm 위로 올라갈 때
  - 0x22: 세트1 관절1이 135.06°까지 밀렸을 때
  - **0x51·0x52 (관절2·3 탈조)**: 트레이 팔이 트레이를 들고 옮기다 실패했을 때 → 부딪혔거나 무게 때문에 위치를 놓쳤다는 뜻이에요
- 알람이 남아 있으면 그 팔의 다음 명령이 전부 무시돼요. 그래서 해제해야 이어서 움직여요.

**알아둘 점**
- 2026-11-02 시연에서 난 알람은 **좌표를 잘못 넣었을 때** 생긴 거였어요. 로봇에 너무 가까운 자리(반경 199mm)와 관절 끝 각도(133.7°)였어요.
- 알람을 해제해도 **목표 자체가 못 닿는 자리면 계속 실패**해요. 그때는 좌표를 고쳐야 해요.
- **좌표를 확정한 뒤에도 같은 자리에서 알람이 반복되면** 그 자리를 1~2cm 몸 쪽으로 다시 찍거나, 위로 드는 높이를 줄이면 돼요(`PLACE_LIFT_Z` 30, `LIFT_Z_OFFSET` 50).
- 관절 한계를 **실제로 넘어간** 경우(예: 관절1 135.06°)는 해제만으로 안 풀려요. 팔을 손으로 가운데 쪽으로 옮긴 뒤 `python demo.py home`을 실행하세요.
- **탈조(0x50~0x53)는 지금 코드도 해제만 해요.** 해제하면 빨간불은 꺼지지만 위치가 틀어진 채로 남아요. 탈조 알람이 찍히면 그 단계가 끝난 뒤 반드시 홈 복귀를 하세요. 자동 홈 복귀는 아직 넣지 않았어요(아래 7장 참고).

**좌표 기준 (켤 때 벗어나면 경고가 떠요)**

| 기준 | 값 | 이유 (실측) |
|---|---|---|
| 최대 반경 | 330mm | 넘으면 "명령 무시 → 재전송"이 잦음 (367mm 자리는 매번 재전송) |
| 최소 반경 | 230mm | 199mm에서 위로 들 때 0x12 알람, 238mm는 정상 |
| 관절1 각도 | ±125° | 135°에서 한계 알람 |

## 2. 전시장 모드: 플랫폼 서버가 재시작되면 주문을 못 받는 문제 (2026-11-03 수정됨)

> **수정 (2026-11-03)**: MQTT 대신 Mobius 알림을 직접 받도록 바꾸면서(`local_feed.notify_server`, 포트 `NOTIFY_PORT`) 판정 규칙을 보드 main과 같게 맞춤.
> 알림은 "직전 seq와 다르면 받음", 5초 조회는 "직전보다 클 때만 받음". 그래서 seq가 1부터 다시 시작해도, 다른 곳이 큰 seq를 올린 뒤에도 알림으로 따라감.
> (2026-11-02 전시장 시험에서 테스트 seq 13 다음에 플랫폼이 seq 4를 올린 사례가 있었음 - 예전 규칙이면 그 뒤 주문을 전부 버렸을 상황)
> 아래는 수정 전 기록.
>
> **남은 경우 (2026-11-04 검토)**: 플랫폼팀이 Mobius를 **초기화해서 구독까지 지워지면** 알림이 안 오고, 5초 조회는 작아진 seq를 버려서 주문을 못 받아요(보드 main도 같음).
> 플랫폼 서버를 재시작만 하면 구독이 남아 있어서 괜찮아요. 초기화했다고 들으면 → 구독 3개 다시 등록 + 로봇 프로그램 2개 재시작 (`운영_매뉴얼.md` 자주 생기는 문제).


**문제**
- 전시장용 `local_gateway.py`는 MQTT와 5초 조회 두 경로로 주문을 받아요.
- 같은 메시지가 두 번 오거나 늦게 온 옛날 메시지를 거르려고, `local_feed.py`는 **순서번호(seq)가 지금까지 받은 것보다 작거나 같으면 버려요.**
- 그런데 플랫폼 서버(Mobius)를 재시작하면 seq가 **1부터 다시 시작해요.** 2026-11-02에 학교 Mobius에서 seq=1로 초기화된 걸 확인했어요.
- 그러면 우리 프로그램은 새 주문을 전부 "옛날 메시지"로 보고 버려서 **아무 반응을 안 해요.** 에러도 안 떠서 알아차리기 어려워요.

**당장 대처**
- 플랫폼 서버를 재시작했다고 들으면 **우리 `local_gateway.py`도 껐다 켜기.** 켤 때 기준이 새로 잡혀요.

**코드로 고치는 방법 (필요해지면)**
- 스냅샷에 들어 있는 갱신 시각(`updated_at`)을 같이 봐요.
- seq가 작아졌어도 **`updated_at`이 마지막으로 받은 것보다 최신이면 "서버가 재시작됐다"고 보고 받아들이고**, 기준 seq를 새로 잡아요.
- 늦게 도착한 진짜 옛날 메시지는 `updated_at`도 옛날이라 그대로 걸러져요.
- 수정 위치: `local_feed.py`의 `SnapshotInbox.submit()`.

**참고**: 학교 Mobius 시험용 `pc_gateway.py`는 통합 저장소에서 뺐어요.

## 3. 트레이 팔 좌표는 `.env`의 `LAYOUT=design` 한 줄에 달려 있음

- 지금 트레이 팔은 **도면으로 추정한 좌표**(`pose_tray_design.json`)를 써요. 실물 트레이가 아직 없어서 찍은 값이 없어요.
- 이 값은 `.env`에 `LAYOUT=design`이 있을 때만 읽혀요. **이 줄을 지우면 트레이 팔 좌표가 없어서** 매 주문 실패를 보고하고 fault가 나요.
- 옛날 시험 배치 트레이 좌표는 `pose_tray_20261008.json`으로 보관만 하고 쓰지 않아요.
- **실물 트레이가 오면 할 일**
  1. 트레이 집는 자리와 놓는 자리를 찍어서 `pose_tray.json`으로 저장하기(찍은 값이 최우선).
  2. 여러 개 쌓였을 때 집는 높이가 바뀌는 처리를 추가하기(트레이 1개당 약 35mm).
- 키캡 세트1·2는 실물에서 찍은 값(`pose_set1.json`, `pose_set2.json`)을 써서 `LAYOUT`과 상관없어요.

## 7. 알람 처리 방식 — 자동 해제 / 사람 조치 / 충돌 구분 (이사님 피드백, 2026-11-02 정리)

### 7-1. 방향 (사용자 결정)
- **웬만한 알람은 자동 해제하고 계속 진행해요.** 지금 코드가 이미 이렇게 동작해요.
- 자동 해제로 안 풀리는 두 경우만 **따로 구분해서 알려요.**
  - **사람 조치**: 사람이 손으로 옮기거나 전원을 다시 켜야 풀리는 경우
  - **충돌**: 부딪혀서 위치가 틀어진 경우. 주변 확인 + 홈 복귀가 필요해요

### 7-2. 알람 번호 → 3가지 분류 (Dobot 공식 알람 설명서 기준)

| 분류 | 알람 번호 | 뜻 | 처리 | 사람이 할 일 |
|---|---|---|---|---|
| **자동 해제** | 0x00~0x01 | 재시작 후 남은 알람, 알 수 없는 명령 | 해제 후 계속 | 없음 |
| | 0x10~0x15 | 목표점이 못 가는 자리 (명령만 거부, 팔은 안 움직임) | 해제 후 계속 | 같은 자리에서 반복되면 좌표 다시 찍기 |
| | 0x20~0x22 | 이동 중 범위·관절 한계 넘음 | 해제 후 계속 | 반복되면 좌표·경로 수정 |
| | 0x30~0x33 | 관절 속도 초과 | 해제 후 계속 | 반복되면 속도 낮추기 |
| **사람 조치** | 0x40~0x49 | 관절이 한계 각도에 닿아 있음 (빠져나와야 풀림) | 그 팔 멈춤 | 잠금 버튼 누르고 팔을 가운데 쪽으로 옮기기 → 홈 |
| | 0x02~0x04 | 파일 시스템 / 내부 통신 / 각도 센서 오류 | 그 팔 멈춤 | 로봇 전원 껐다 켜기 → 홈 |
| **충돌** | 0x50~0x53 | 관절 1~4 탈조 (부딪혀서 위치를 놓침, 해제해도 위치가 틀어진 채 남음) | 그 팔 멈춤 (키캡을 든 채 홈으로 가지 않음) | 걸린 물체 치우기 → 홈 (`demo.py home`) |

- 사람 조치로 분류하는 0x40~0x49는 **해제를 한 번 해봤는데도 남아 있을 때만**이에요. 잠깐 닿았다 빠지는 경우는 저절로 풀려서 자동 해제로 처리돼요.
- 2026-11-02에 실제로 나온 것
  - 0x12(자동 해제): 세트1·2 좌표 잘못 넣었을 때
  - 0x22(자동 해제): 세트1 관절1 135.06°
  - 0x51·0x52(충돌): 트레이 팔이 트레이를 들고 가다 실패

### 7-3. 어떻게 알려주나 — 3가지 경로

**① 창고 노트북 화면 + 소리 (바로 가능, 우리끼리 구현)**
- 화면에 눈에 띄는 박스로 띄워요.
  ```
  ==================== [충돌] 세트1(COM6) ====================
   관절2 탈조 (0x51) — 키캡2 놓으러 가는 중, 좌표 (227.2, -234.9, 70.5)
   할 일: 걸린 물체 치우기 → demo.py home → 관리자 페이지에서 fault 해제
  ===========================================================
  ```
- 노트북에서 경고음을 내요. 사람 조치와 충돌은 소리를 다르게 할 수 있어요.

**② 알람 기록 파일 (바로 가능)**
- `runtime/alarm_log.csv`에 시각, 팔, 알람 번호, 분류, 동작 단계(집기·놓기·빠지기), 목표 좌표를 한 줄씩 남겨요.
- 시연이 끝나면 "어느 자리에서 어떤 알람이 몇 번"인지 표로 뽑아서 이사님께 보고할 수 있어요.

**③ 플랫폼 관리자 페이지 (플랫폼팀 협의 필요)**
- 지금 우리가 실패를 보고하면 플랫폼은 원인과 상관없이 fault 하나로만 표시해요.
  - 키캡 팔 → `keycap_pack_failed`
  - 트레이 팔 → `tray_load_failed`
- **같은 방식이 이미 있어요.** 키캡 카트리지는 `cnt_keycap_status`에 `reason`을 붙여 보내면, 플랫폼이 이유별로 다른 fault를 띄워요.
  - `reason: jammed` → `keycap_cartridge_jammed`
  - `reason: motor_failure` → `keycap_cartridge_motor_failure`
  - 키캡 벨트도 `section: "01"/"02"`를 붙여 `keycap_01_belt_jammed` / `keycap_02_belt_jammed`로 나눠요.
- 로봇팔 보고에도 `reason`을 붙이자고 제안하면 돼요.
  ```json
  {"order_id": "ord_xxx", "keycap2": "failed", "reason": "collision"}
  {"order_id": "ord_xxx", "status": "failed", "reason": "manual"}
  ```
  | reason | 플랫폼 fault (제안 이름) | 관리자 페이지 안내 |
  |---|---|---|
  | (없음) | `keycap_pack_failed` / `tray_load_failed` (지금 그대로) | 일반 실패 |
  | `collision` | `keycap_arm_collided` / `tray_arm_collided` | 주변 확인 → 홈 복귀 → 해제 |
  | `manual` | `keycap_arm_manual` / `tray_arm_manual` | 팔 옮기기 또는 전원 재시작 → 해제 |
- 플랫폼이 `reason`을 아직 모르면 그냥 무시하고 지금처럼 동작하므로, 우리가 먼저 붙여서 보내도 문제는 없어요.
- **보드 Flask도 같이 고쳐야 해요 (2026-11-04 확인).** 전시장에서는 우리 보고가 보드 Flask(`board/app.py`의 `/report/keycap-robot-arm`, `/report/tray-robot-arm`)를 거쳐 Mobius로 가는데, 이 두 라우트는 `order_id`·결과만 골라서 넘겨요. 그래서 `reason`을 붙여도 플랫폼까지 안 가요 → 보드팀과 함께 수정.

### 7-4. 진행 순서 제안
1. ①②를 먼저 넣기 (우리 코드만 고치면 됨, 운영 흐름은 그대로)
2. 플랫폼팀에 ③ `reason` 필드 제안 (위 표를 그대로 전달)
3. 플랫폼에 반영되면 우리 보고에 `reason` 붙이기

## 10. 놓은 뒤 "들기·당기기" 생략 (`PLACE_LIFT`) — 2026-11-02 시험

**무엇이었나**
- 키캡(트레이)을 놓은 뒤 순서: 그리퍼 열기 → **위로 30mm 들기 → 멈춤** → (반경 300mm보다 먼 자리면) **몸 쪽 300mm까지 당기기 → 멈춤** → JUMP로 다음 집기 자리.
- JUMP도 출발할 때 스스로 20mm 올라가요. 그래서 "들기 → 멈춤 → 또 들기 → 이동"이 돼서 **놓은 뒤 살짝 움찔**하는 것처럼 보였어요.
- 처음 넣은 이유(10/1 시험 배치): 놓는 자리가 330~367mm로 팔을 다 뻗은 곳이었고, 거기서 바로 JUMP하면 명령이 무시되고 알람이 쌓였어요.

**설정** — `.env`의 `PLACE_LIFT`
- `PLACE_LIFT=1` (코드 기본값): 들기·당기기 함 (예전 방식)
- `PLACE_LIFT=0` (**지금 `.env` 설정**): 놓고 바로 JUMP로 빠짐 (움찔 없음)

**시험 결과 (2026-11-02, 도면 배치 + 실물 좌표, 놓는 자리 292~328mm)**

| | 들기·당기기 함 (1) | 생략 (0) |
|---|---|---|
| 키캡 4개 | 43.0~43.7초 | **32.9초** |
| 트레이 팔 | 11.6~13.0초 | 10.2초 |
| 재전송·알람 | 0회 | 0회 |

→ 키캡 단계가 **약 10초 빨라졌고**(60초 제한 대비 여유 27초), 알람도 없어서 **지금은 `PLACE_LIFT=0`으로 진행**해요.

**결정 (2026-11-02):** 사용자가 실물을 눈으로 확인했어요. 놓은 뒤 움찔이 없고 키캡도 끌리지 않아서 **이 방향(`PLACE_LIFT=0`)으로 진행**해요. 전시장용 `.env.local`에도 같은 값을 넣어요.
